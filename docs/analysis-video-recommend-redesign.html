需求分析 NativeOS 视频跟练 v1 草稿

把「被推荐一堆」改成「我自己挑」

你的两个想法其实解决的是两件不同的事——Supabase 化是技术替换,降低维护成本; 推荐变入口是产品形态变化,直接决定用户看到什么。把它们拆开看,哪件事先做、做到什么程度,会更清楚。

两个核心判断

1
现在的"推荐"页本质是个目录 它把官方所有 series 一次性铺出来,只是按 level/category 做了筛选 UX。资源一多就一脸懵,跟你描述的体感一致。
2
换 Supabase 不解决"被推一堆" 数据源换了,UI 没变,用户体感一样。要彻底解决"主动挑选",得动 UI 和状态机——这是第二件事。
01

当前业务是怎么跑起来的

先把你这套视频跟练的"血管"画清楚——推荐内容从哪来、经过什么、最终落到哪个 UI。

DATA SOURCE
OSS Bucket
TIER 1
内存缓存
TIER 2
SQLite 落盘
UI
视频 tab / 跟练
源数据 中间缓存 用户界面 → nativeos.oss-cn-beijing.aliyuncs.com/videos/official-video-catalog.json

OSS 这条链路,起点是个 catalog JSON

official-video-catalog.json 里登记了所有 series,每条带一个 manifestUrl。应用启动后先拉这个 catalog,再并发拉每个 series 的 manifest,拼成 OssVideoManifest,走"内存 → SQLite → 网络"三级缓存(详见 video-scenes.ts::getOssManifest)。 每个 scene 自己的 info.json 和 aiPractice.json 也是 OSS 上的,按需拉。

三个数据源汇到同一个函数,再分流

getFeaturedVideoScenes() 同时拉三份数据:OSS 官方(series + standalone)、 本地导入(用户自加的 video pack)、云盘引用(user_video_ 开头)。 按"用户视频 → 导入 → 官方"的优先级去重合并,最后 featuredScenesCache 一次性返回。

这个混合数据源被两处 UI 消费

视频 tab(app/(tabs)/videos.tsx)的"推荐"子 tab 直接展示 series 列表; AI 陪练(AiPracticeHome.tsx)的"跟练话题"区也调同一个函数,只是按 getFeaturedVideoScenes 拆成 topic 卡片。所以改一处会同时影响两个入口。

02

用户现在的体感问题

"一脸懵"是个症状,不是病根。拆开看,实际上是三件事混在一起。

H 高频
首屏密度过高

"推荐"tab 进入就是全集,level 6 个 + category 4-5 个,初次用户连哪个适合自己都判断不了。

H 高频
用户对内容没掌控感

官方往这塞什么就显示什么,用户没有"选过"的参与,也没法拒绝不感兴趣的。

M 中频
资源全压在客户端筛选

所有 series 都下发,只是被 client 端用 chip 过滤一次——"用下发替代推荐"是个常见反模式。

M 中频
维护成本高

改一条推荐要发版 OSS JSON,运营自己改不了,得找开发;一次加 10 个视频要小心 manifest 体积别膨胀。

L 低频
冷启动耗时

catalog + N 个 series manifest 并发拉,虽然有 SQLite 兜底,首次冷启仍有可见延迟。

L 低频
跟练话题强依赖

AI 陪练的"跟练话题"完全跟着视频 tab 走,如果视频 tab 数据出问题,跟练话题也会被波及。

03

把需求拆成两件独立的事

它们的目标、风险、影响面都不一样,先分开评估,再决定怎么并。

SUB-A · 技术替换

把推荐配置的存储从 OSS 迁到 Supabase

  • 改的是什么:数据源——official-video-catalog.json 和 series manifest 改用 Supabase 表返回
  • 不改的是什么:UI、缓存逻辑、视频文件本身(videoKey 仍指向 OSS)
  • 收益:运营可以自己改,不用发版;加字段/调分类不用 PR
  • 代价:需要 admin 入口或 SQL Editor 维护;多一次网络依赖
SUB-B · 模式调整

把"推荐"改成"入口",让用户自己挑

  • 改的是什么:状态机——引入"我的跟练"集合,推荐页变成挑选器
  • 不改的是什么:视频文件、字幕、跟练体验本身
  • 收益:首屏短、内容由用户掌控、可以"选过 → 沉淀"形成复访
  • 代价:老用户兼容、迁移策略、新状态在两个 UI(tab + 跟练话题)都要同步

建议执行顺序

先做 SUB-A(低成本,高收益),再上 SUB-B(高成本,需设计)。 如果直接上 SUB-B,数据源还是 OSS,运营在"挑选器"上线后想加内容还是得发版——所以先把维护通路打开,再调整产品形态,效率最高。

04

SUB-B 的三种模式——你挑一种

三种模式我都说一下利弊。点击卡片可模拟"选中",下面会有对应的方案建议。

A · 双层并列

推荐 tab 改双层
  • "我的跟练"放顶上,初始为空
  • 下面紧跟"推荐资源库"全量
  • 资源库卡片 +"加入我的"按钮
  • 用户用按钮显式加入
改动最小·老用户可一键"全选已浏览的"

B · 拆成两个 tab

推荐 / 我的跟练 拆开
  • 原"推荐" tab 改名为"资源库"
  • 新增"我的跟练" tab,初始为空
  • 首次进入空态,引导去资源库挑选
  • 挑选完成后回到"我的跟练"开始练
心智最清晰·老 tab 名要换,迁移文案要写

C · 收藏式

先保留收藏 tab,加入口
  • "推荐" tab 内容原样,加"⭐ 加入"按钮
  • 已加入的会自动出现在"收藏" tab
  • 0 状态结构改动,只是把"收藏"语义扩大
  • 数据用现成的 video_user_meta 即可
改动最小·但"收藏"语义被拉伸,不太推荐

我的建议:模式 B

三个里面我推荐 模式 B。"推荐" 这个词本身暗示"主动塞",跟"用户挑选"在心智上冲突;改成"资源库" (或"官方资源库"),让"我的跟练"独立成 tab,语义清楚。老用户的兼容用一次性的"已浏览过"批量加入即可,不会丢数据。 唯一成本是 tab 文案和空态引导要重新设计。

05

数据模型怎么落——两张表就够

视频文件本身仍在 OSS,Supabase 只管"目录"和"用户选择"。这样存储便宜、迁移轻、不动 videoKey。

official_video_series

原来 official-video-catalog.json::series 的内容。

字段类型说明
idtext PKsceneId 前缀,例如 travel-bucket-list
titletext中文展示名
leveltextA1..C2
categorytext综合 / 旅行 / 社交 …
typetextvlog / dialogue / lecture / film
descriptiontext长描述
cover_urltextOSS 上的封面
tagstext[]运营标签,排序辅助
sort_orderint运营手动排序,默认 0
manifest_urltext该 series 的子 manifest(仍在 OSS)
resource_base_urltextseries 资源根 URL
is_publishedboolfalse 即下架,前端过滤掉
created_attimestamptz运营录入时间
updated_attimestamptz触发器自动维护
user_picked_video_series

记录"我挑了哪些 series 进我的跟练"。一行一个 series,新加/移除都改这张表。

字段类型说明
idbigserial PK内部主键
user_iduuid FK→auth.users用户
series_idtext FK→official_video_series挑的 series
picked_attimestamptz加入时间,用于排序
last_practiced_attimestamptz最后练过,跟练 tab 排序用
is_pinnedbool是否置顶(置顶的永远在最上)

唯一约束 (user_id, series_id)·RLS 限定用户只能看/改自己的行·删除 series 时级联清理

为什么是 series 而不是 episode

现在 video-scenes.ts 在 series 维度给用户展示,episode 是在 series 详情里再展开。 "用户挑什么"这个动作,粒度放在 series 比较自然——一次性加进整个系列(比如"旅行清单 5 集"), 而不是单集。episode 级别的"加入/移除"会让状态空间变大,但收益不大。如果你后面想精确到单集,在这张表加 episode_id 即可,不需要重建表。

Series 内部的 manifest 还放 OSS

manifest_url 仍指向 OSS,这一层不迁。理由:剧集多的时候 episode manifest 体积不小, 留在 OSS 配合 virtual-hosted + HTTP 缓存最省;Supabase 只承担"目录"职责,不大材小用。如果以后要 做"按用户定制清单"或"动态字幕",再考虑把 manifest 也搬上来。

06

兼容性与风险盘点

最容易被忽略的是"老用户"——他们已经在用,新模式上线时不能让他们看见一个空荡荡的首页。

风险点等级处理思路
老用户进入新模式看到"我的跟练"为空 高 迁移期做一次"自动加入":凡是 video_user_meta.lastPracticedAt > 0 的 series,自动写入 user_picked_video_series;用 is_pinned=true 标记,用户能"撤销"
"推荐"和"我的跟练"两个 tab 的内容去重 高 前者是 catalog 全集,后者是 user_picked_video_series 过滤,数据源不同自然去重;不需要在同一函数里合并
AI 陪练"跟练话题"区如何联动 高 跟练话题建议只展示"用户已加入"的 series 派生出来的 topic;否则就是历史重演,继续"被推一堆"
运营改 Supabase 表但没 reload,客户端拿到旧缓存 中 现在已经有 SQLite 三级缓存,新数据源的缓存策略照搬;另外可以加一个 updated_at 头部,客户端发现 manifest version 变了就强制 refresh
RLS 没配好导致用户能看别人的跟练 高 user_picked_video_series 必须 RLS: user_id = auth.uid();前端不绕过,service_role 不在端上用
Series 录入字段过多,运营填表痛苦 中 运营配置面板的设计原则:能砍的字段先砍,能合并的合并。优先最小可用方案,二期再扩展。series 表里 description / cover_url / sort_order / is_published 这几个就够用
迁移期间 OSS 和 Supabase 双源 中 迁移完后下架 OSS 上的 catalog.json(可以保留一个 410 状态或保留只读副本);客户端读取新表,失败时 fallback 到旧 JSON,保证兼容
冷启动多一次 Supabase 网络请求 低 Supabase 免费版有 RLS 缓存 + 客户端 SQLite 落盘,实测比拉 N 个 series manifest 快;不构成性能问题
07

落地路径——分四步,每一步可独立验证

按"先骨架后体验"拆,每一步都有可验收的产物,不至于一次性 merge 半个 app。

  1. 阶段 1 · 数据迁移(纯后端,1-2 天)

    写 Supabase migration 建表 + RLS + 触发器;用脚本把现有 OSS JSON 全部导进 official_video_series; 跑通 SELECT * FROM official_video_series WHERE is_published = true 跟 OSS 拉到的内容对账。

    交付物:两张表的 migration · 一份对账报告

  2. 阶段 2 · 读链路切换(只动 read,1-2 天)

    改 getOssManifest 行为:把"从 OSS 拉 catalog"换成"从 Supabase 拉 series 列表 + 再从 OSS 拉对应 manifest"。 getFeaturedVideoScenes 函数签名不变,UI 完全无感。验证点:视频 tab "推荐" 跟以前长得一模一样。

    交付物:video-scenes.ts 替换 + 灰度开关(读 Supabase vs 读 OSS)

  3. 阶段 3 · 用户选择 API(1-2 天)

    新增 lib/content/user-picked-series.ts,封装 listMyPickedSeries / pickSeries / unpickSeries / pinSeries 四个方法; 写 user_picked_video_series 的 RLS;跑通本地+Supabase 联调。

    交付物:TS API + 4 个集成测试 + 一次性的"老用户自动加入"脚本

  4. 阶段 4 · UI 切换(2-3 天)

    视频 tab 顶部 tab 顺序调整为「我的跟练 / 资源库 / 导入 / 历史」; "资源库"卡片加"加入我的"按钮;"我的跟练"空态写引导;AI 陪练的"跟练话题"区改成只展示已加入的。 配一个 feature flag,逐步放量。

    交付物:UI 改完 + feature flag + 用户分批放量

每一步的验收标准(我列好了你照着验)

  • 阶段 1:对账脚本输出 0 diff
  • 阶段 2:打开 app,视频 tab 内容跟旧版完全一致;下掉 OSS catalog 也不报错
  • 阶段 3:在 Supabase 表里手动加一行,客户端能在 <1s 内查到;同一行别的用户看不到
  • 阶段 4:新用户首次进入"我的跟练"看到空态;加入 1 个 series 后立刻出现;关掉重开还在;卸载重装仍然在(因为是云端)
